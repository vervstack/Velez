# PostgreSQL replication, failover and balancer — design

Status: draft, 2026-11-24. Cards: Verv board `1YiKjezm` (HAProxy), `vXL8jcD4` (PgBouncer),
`OtRWl6Uk` (Odyssey); Artel board #460 (`8IEOCkkM`, continuous replication + failover),
#461 (`jYoUq3zi`, one-shot replication — shipped).

## Goal

User story: production pg behind a slow link, fresh second instance. Copy everything
(schema, data, roles, enums), put a balancer in front, switch writes to the new instance,
turn the old one into a replica streaming back over the slow link. Downtime during the
switch is acceptable and user-controlled.

## Decisions (locked with the user)

- Replication mechanism: **physical streaming** first; design stays agnostic so **logical**
  replication can be added as a mode later (`mode: physical|logical` in the job payload).
- Balancer: **HAProxy** first, as a standalone Velez-managed service; PgBouncer and Odyssey
  are follow-up alternatives behind one "balancer type" abstraction.
- Dependent services during "change master" are **stopped by the user**, not by Velez.
- `wal_log_hints` is **not** forced by default — it is an explicit action on the pg service
  page with a restart warning (see "Replication readiness").
- Replication slot on master: **on by default**, user can uncheck when setting up replication.

## Feature A — replication readiness (pg service page)

Physical replication and fast failover need master-side settings that require a restart:

- `wal_level = replica`
- `wal_log_hints = on`  (precondition for `pg_rewind` — without it the old master can only
  be re-integrated by a full re-copy)
- `max_wal_senders >= 10`, `max_replication_slots >= 10`

UI: pg instance service page gets an **Enable replication** button. Dialog lists the
settings that will be applied and warns: "the server will be restarted" — Yes/No.
Backend: a job (`enable_pg_replication_readiness`) applies the settings
(`ALTER SYSTEM SET` + config check), restarts the container, waits for ready. Idempotent:
already-set values are skipped, restart is skipped when nothing changed.

New pg instances created by Velez get these settings **at creation time** (no restart
needed then) — readiness action is only for pre-existing instances.

## Feature B — HAProxy balancer service (card 1YiKjezm)

New instance type `haproxy_instance` mirroring `pg_instances` (storage row + labels +
instance page):

- Velez deploys HAProxy as a standalone service; config generated by Velez.
- Backends = pg instance names; `option pgsql-check` health check on the master backend.
- **Select master** dropdown on the balancer's page: rewrites the backend config and
  reloads HAProxy (reload keeps listeners; clients re-dial).
- Services point their DSN at the balancer; switching masters then never touches service
  config.
- Statelessness: balancer config derives from its instance row (cluster) / container
  labels + mounted config volume (single-node) — never from process memory.
- Abstraction seam for PgBouncer/Odyssey: balancer type field + per-type config renderer;
  one shared "select master" UI.

## Feature C — replication setup (card #460)

New job `setup_pg_replication` with payload:

```
source instance | plain dsn
target instance | plain dsn
mode: physical | logical      (only physical implemented now)
use_slot: bool = true         (checkbox in UI, default checked)
```

Physical flow:

1. verify source readiness (Feature A settings present; fail with pointer to the button);
2. create replication slot on source when `use_slot`;
3. `pg_basebackup -X stream -z` from source into the target instance's empty data volume
   (the slow-link pain point: one full compressed copy);
4. start target with `primary_conninfo` + `standby.signal`; streaming begins;
5. verification: replica is `streaming`, replay LSN advancing.

Slot trade-off (shown as tooltip on the checkbox): with a slot the replica survives any
network outage and resumes where it stopped, but an abandoned replica makes the master
keep WAL forever — disk fills. Without a slot, a replica offline longer than the retained
WAL window needs a full re-copy.

UI "fully in sync" signal: per-replica status on the pg instance page — state
(streaming/catchup/down), lag bytes and seconds from `pg_stat_replication` +
`pg_last_wal_replay_lsn()`, and a green **in sync** badge when replay LSN == source
current LSN. Polled via the existing instance-status path.

## Feature D — change master (failover)

**Change master** button on the balancer (or pg instance) page, gated on the target
replica being in sync (badge green); disabled with a hint otherwise. User stops dependent
services beforehand (their responsibility, stated in the dialog).

Sequence (one durable job):

1. confirm target replica fully caught up (`replay_lsn == source current lsn`);
2. stop writes guard: verify no active connections on source besides replication
   (warning, not a hard block — user owns downtime);
3. `pg_ctl promote` on the target replica;
4. repoint HAProxy master backend to the new instance, reload;
5. re-integrate the old master as replica of the new one — user picks the strategy in the
   dialog, each with a tooltip:
   - **Fast catch-up (pg_rewind)** — "Reuses the old master's existing data and copies
     only pages changed since the switch. Minutes instead of a full copy. Requires
     replication readiness (wal_log_hints) to have been enabled before the switch."
     Falls back with an error if the precondition is missing.
   - **Wipe and re-copy (pg_basebackup)** — "Erases the old master's data and copies
     everything over the network from scratch. Slow on large databases and slow links,
     but always works."
6. old master rejoins as streaming replica (slot as chosen).

## Data model notes

- Cluster mode: pg instance rows gain replication fields (role, source, slot name, mode).
- Single-node: replication topology lives on container labels (`velez.pg.role`,
  `velez.pg.source`, `velez.pg.slot`) — read back per the statelessness rule.
- Migration `NNN_pg_replication.sql` when the cluster-mode columns land.

## Slices

1. Feature A: readiness job + pg-page button + restart dialog (backend + UI).
2. Feature B: HAProxy instance type + select-master UI (card 1YiKjezm).
3. Feature C: setup_pg_replication (physical) + in-sync status UI.
4. Feature D: change-master job + dialog with strategy choice.

Each slice is independently testable end to end; e2e: two pg containers on one Docker
host emulate source/replica (existing e2e pg suite patterns).
