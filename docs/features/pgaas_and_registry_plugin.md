# Postgres-as-a-Service & the Registry plugin

Two features, one shared mechanism: **builtin vervonomicon descriptors**.

Velez ships `.verv/` descriptors for the containers it provisions on the user's behalf
(`postgres`, `registry`). They are embedded into the binary and fed through the *existing*
`Parse` -> `MergeEnvironment` -> `BoxResolver.ResolveRequest` path, so a Velez-provisioned
container is deployed by exactly the same code as a user's service. No parallel provisioner.

Per `docs/features/vervonomicon.md`'s rule "no descriptor file ever contains a credential",
a builtin descriptor declares only *shape* — image, ports, volumes, healthcheck, box. The
service layer overlays the generated name / env / volume / exposed port onto the resolved
`CreateSmerd.Request` before handing it to `CreateNewDeploy`.

## 1. Secret store — the Svarog fallback

`velez.secrets` is a **deliberately poor** secret store. One day a **Svarog** service (a Vault
alternative) will hold these values; this table is the fallback for a user who does not want to
run one. The seam that makes that swap possible is the `secrets.Store` interface — nothing
outside `internal/service/secrets` may touch the table directly.

### Table

```sql
CREATE TABLE velez.secrets
(
    id         INT8 GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    scope      TEXT        NOT NULL,
    owner      TEXT        NOT NULL,
    key        TEXT        NOT NULL,
    value      TEXT        NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    UNIQUE (scope, owner, key)
);

COMMENT ON COLUMN velez.secrets.value IS
    'Plaintext. This table is the fallback secret store used when no Svarog instance is '
    'configured; encryption at rest is Svarog''s job, not this table''s. Reachable only '
    'through internal/service/secrets.Store.';
```

### Reference

`domain.SecretRef{Scope, Owner, Key}`, canonical string form `scope/owner/key`. Other tables
(`velez.pg_instances.secret_ref`, `velez.registries.secret`) store **that string, never a value**.

### Interface

```go
// internal/service/secrets
type Store interface {
    Put(ctx context.Context, ref domain.SecretRef, value string) error
    Get(ctx context.Context, ref domain.SecretRef) (string, error)
    Delete(ctx context.Context, ref domain.SecretRef) error
    // ListRefs returns keys only - never values.
    ListRefs(ctx context.Context, scope, owner string) ([]domain.SecretRef, error)
}
```

`dbStore` is the only implementation today, over `storage.SecretsStorage` (postgres + static
backends, mirroring `internal/storage/registries`). A future `svarogStore` implements the same
interface and `internal/app/custom.go` picks between them.

## 2. Builtin vervonomicon descriptors

```
internal/service/service_manager/vervonomicon/builtin/
    builtin.go              go:embed + Read(name) (map[string][]byte, error)
    postgres/
        vervonomicon.yaml
        deployment.yaml
    registry/
        vervonomicon.yaml
        deployment.yaml
```

`Read` returns the same flat `map[string][]byte` keyed by path-relative-to-`.verv/` that
`ImageSource.Read` returns, so `Parse` and `MergeEnvironment` consume it unchanged.

`verv.SourceKindBuiltin SourceKind = "builtin"` is added alongside image/repo/pushed, and the
matching `VervonomiconSource` proto enum value.

## 3. Postgres as a Service

**A PG instance is a normal Velez service.** It gets `velez.services`,
`velez.deployment_specifications` and `velez.deployments` rows through the ordinary
`VervServicesService.CreateNewDeploy` path, and the existing deploy watcher creates the
container. Status, environment, image, container id and deploy history are read from those
tables and from `ListSmerds` — never duplicated.

Only the pg-specific facts get their own linked table:

```sql
CREATE TABLE velez.pg_instances
(
    service_id INT8        NOT NULL PRIMARY KEY REFERENCES velez.services (id) ON DELETE CASCADE,
    db_name    TEXT        NOT NULL,
    username   TEXT        NOT NULL,
    secret_ref TEXT        NOT NULL,
    port       INT4        NOT NULL DEFAULT 5432,
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
```

### Create flow (service layer, no jobs handler)

```
generate db_name / username / password
    -> secrets.Store.Put(ref)                       ref = pgaas/<service name>/password
    -> builtin.Read("postgres") -> Parse -> ResolveRequest
    -> overlay: name, POSTGRES_DB/USER/PASSWORD env, volume, exposed port, environment, box
    -> Services().UpsertService(name)
    -> CreateNewDeploy(name, descriptor, request)   deploy watcher takes it from here
    -> upsert velez.pg_instances row
    -> if owner_service given: ServiceResources().UpsertResource(owner, name, "postgres")
```

### Drop flow

Existing `VervServicesService.Remove` + delete the satellite row + `secrets.Store.Delete`.

### Isolation

`separate_instance` only — one postgres container per instance. `shared_pool` (a database inside
the statefull_pg cluster postgres) is surfaced in the UI as a disabled option.

### API

New `api/grpc/pgaas_api.proto`, service `PostgresAPI`:

| RPC | HTTP |
|---|---|
| `ListPgInstances` | `POST /api/postgres/list` |
| `CreatePgInstance` | `POST /api/postgres/create` |
| `DropPgInstance` | `POST /api/postgres/drop` |
| `GetPgInstanceCredentials` | `GET /api/postgres/{name}/credentials` |

`ListPgInstances` never returns a password. `GetPgInstanceCredentials` is the only RPC that
resolves a `secret_ref` to its value.

## 4. Registry plugin

A local container registry bootstrapped the same way stateful mode is — through `EnablePlugin`
— but deployed from the builtin `registry` descriptor rather than an ad-hoc container pattern.

- `VervPluginType registry = 7`
- `EnableRegistry { optional uint32 expose_to_port = 1; optional string username = 2; }` joins the
  `EnablePlugin.Request` oneof.
- Jobs handler `enable_registry` (`internal/jobs/enable_registry.go`), so the UI reuses the
  existing task-progress screen shape:

```
generate credentials (username default "verv", random password)
    -> secrets.Store.Put(ref)                       ref = plugin/registry/password
    -> write htpasswd (bcrypt) into the registry's named volume (reuse copy_to_volume)
    -> builtin.Read("registry") -> Parse -> ResolveRequest -> overlay
    -> Services().UpsertService("registry") + CreateNewDeploy
    -> upsert velez.plugins row
    -> upsert velez.registries row: type generic_v2, url http://<host>:<port>,
       username, secret = the secret ref string
```

The registry becomes immediately usable for deploys because it lands in `velez.registries`.

## 6. Deliberately out of scope

- Wiring vervonomicon `must_provision` postgres resources to this provisioner —
  `CreateDeployFromVervonomicon` keeps logging them. Natural follow-on once this lands.
- `shared_pool` isolation.
- Svarog itself. Only the `secrets.Store` seam exists.
